# TAD — Termux Android Dev

`tad` builds, installs and tests Kotlin + Jetpack Compose Android apps entirely
on an Android phone inside Termux. No Android Studio, no PC, no root, no proot.

Commands are `tad <command>`; the same scripts also exist as `tad-<command>`.

## Preflight — always do this first

```bash
tad doctor
```

It exits non-zero and lists every problem it finds (missing JDK, wrong `aapt2`
architecture, missing SDK platform, unshimmed `adb`, no device). Fix those before
anything else. If `tad` itself is missing, the tool is not installed — see below.

## Installing (only when the user asks)

```bash
cd ~/.local/share/TAD && ./bin/tad-setup && source ~/.bashrc
```

This downloads several hundred MB. Ask before running it unless the user already
asked to set up the toolchain. It is idempotent, so it is safe to re-run after a
failure or a dropped connection.

## Command map

| Goal | Command |
|---|---|
| Create a Compose project | `tad new <Name> --package <id>` |
| Make an existing project buildable | `tad init [dir]` |
| Build a debug APK | `tad build` |
| Build a release APK | `tad build release` |
| Build, install and launch | `tad run` |
| Install an existing APK | `tad install <apk>` |
| JVM unit tests | `tad test unit` |
| On-device Compose UI tests | `tad test instrumented` |
| Both test kinds | `tad test all` |
| Clean build output | `tad clean [--daemon\|--all]` |
| adb pair/connect/devices/logcat/phantom | `tad adb <cmd>` |

## Rules that matter

1. **On-device builds are slow** — minutes even for a small app, and a cold
   dependency download can take far longer. Run long builds in the background
   and wait for them; a quiet build is not a stalled build.
2. **Trust the exit code, not the log.** `tad build` exits non-zero when Gradle
   prints `BUILD SUCCESSFUL` but the APK is invalid: it verifies
   `AndroidManifest.xml`, `resources.arsc`, dex and the signature itself.
3. **Run `tad` from the project root** — the directory containing
   `settings.gradle.kts`. `tad build` refuses to run anywhere else.
4. **AGP 9 compiles Kotlin itself.** Never add the `org.jetbrains.kotlin.android`
   plugin to a project generated by `tad new`; it fails the build. The Compose
   compiler plugin version must equal the Kotlin Gradle plugin AGP bundles (see
   `tad.conf`).
5. **Release APKs are unsigned** unless the project defines a `signingConfig`.
   `tad build release` warns about that; it is not a failure.
6. **The device is real hardware.** There is no emulator workflow — use `tad run`
   and `tad adb` against the phone.
7. **Do not kill the adb server during a build.** AGP's on-device tests depend on
   the connection.

## Worked example

```bash
tad new MyApp --package com.example.myapp
cd MyApp
tad build                 # verify the debug APK assembles
tad run                   # install and launch on the phone
tad test unit
tad test instrumented
```

## Pairing with the device (adb over loopback)

Termux and adb run on the same phone, so adb always talks to `127.0.0.1`. The
pairing port and the connect port are different; read both from
**Developer options → Wireless debugging**.

```bash
tad adb pair <pairing-port> <code>
tad adb connect <connect-port>
tad adb status
```

## Troubleshooting

| Symptom | Action |
|---|---|
| `Exec format error` for `adb` or `aapt2` | `tad doctor`, then re-run `tad setup` to restore the adb symlink |
| Build dies part-way through | Phantom-process killer: `tad adb phantom off` (re-enable with `tad adb phantom on`) |
| `OutOfMemoryError` during a build | Lower `GRADLE_JVMARGS` in `tad.conf`, then `tad setup` |
| No device connected | `tad adb connect <port>`, or pair again |
| `... aapt2FromMavenOverride ... experimental` warning | Expected; the option is required for on-device builds |
